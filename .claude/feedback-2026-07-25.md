## Punto 1 — La demo dava "chiave API non valida"

Non era un errore del cliente. La route `/api/public/contact` fa
`if (!expected || apiKey !== expected) return 401`: il secret `PUBLIC_API_KEY` non era
impostato in Lovable Cloud, quindi `expected` era `undefined` e **ogni** richiesta veniva
rifiutata, anche con la chiave corretta. Verificato dall'esterno: 401 sia con chiave sbagliata
sia con quella giusta.

**Azione:** impostare `PUBLIC_API_KEY = test-oltremani-2026` in Lovable → Cloud → Secrets.
Nessuna modifica al codice. Vedi il riquadro in `architecture.md`.

## Punti 1 + 2 — Gerarchia dei gruppi

**Decisione presa:** antenne e gruppi informali **sotto ogni APS/ODV**.

```
Alessandria (APS/ODV)
├── Antenne
│   └── … comuni assegnati
└── Gruppi informali
    └── … comuni assegnati
Ragusa (APS/ODV)
├── Antenne
└── Gruppi informali
…  × 8
```

### Cosa serve davvero

La gerarchia **è già supportata**: `res_partner_category.parent_id` è una self-FK e
`visible_category_ids()` scende ricorsivamente sui discendenti. Quindi:

- **niente tabella nuova**
- un coordinatore assegnato a "Alessandria (APS/ODV)" vedrà automaticamente anche Antenne e
  Gruppi informali sottostanti, senza configurazione aggiuntiva. È già così, gratis
- le città **non** diventano categorie: `res_city.category_id` punta già a una categoria, quindi
  basta farlo puntare alla sottocategoria giusta (es. Modica → "Ragusa / Antenne").
  L'unità di visibilità resta il gruppo, non il singolo comune

L'unica cosa che manca è **come si chiama un gruppo**: oggi `category_type` distingue solo
`territorial` e `system` (`system` = `Validation`), e non c'è modo di dire "questo è un'APS/ODV,
quello è un'antenna".

```sql
ALTER TABLE res_partner_category ADD COLUMN group_kind text;
ALTER TABLE res_partner_category ADD CONSTRAINT res_partner_category_group_kind_check
  CHECK (group_kind IS NULL OR group_kind IN ('aps_odv','antenna','informale'));
```

### Dati

1. marcare le 8 categorie territoriali esistenti come `group_kind='aps_odv'`
2. creare i 16 figli (Antenne + Gruppi informali per ciascuna)
3. i 107 capoluoghi restano agganciati alla radice APS/ODV: sono la sede, non un'antenna.
   I comuni non capoluogo si assegneranno ad Antenne o Gruppi informali man mano
4. **da chiarire in videocall:** la nona categoria esistente,
   `1 - GRUPPI INFORMALI (NON APS/ODV)`, è un gruppo piatto legacy. Va convertita in
   `informale` sotto una specifica APS/ODV, oppure archiviata? Non ha un territorio proprio

### UI

- `groups.tsx` già rende l'albero ricorsivamente: aggiungere un badge per `group_kind`
- `category-dialog`: select per `group_kind`
- il select "Gruppo padre" dovrebbe impedire combinazioni assurde (un'APS/ODV figlia di
  un'antenna). Nice-to-have, non blocca

## Punti 5 + 7 — Tipo di persona e ruoli

**Decisioni prese:** sono **due campi distinti**, e il ruolo è **multiplo**.

### Campo A — verso della relazione (sostituisce attivista/cittadino)

Una sola scelta per persona. Sostituisce `partner_type`, che oggi ha
`CHECK (partner_type IN ('individual','activist','citizen'))` — vincolo aggiunto il 2026-07-25,
va aggiornato insieme ai valori.

| Nuovo valore | Etichetta |
|---|---|
| `seeks_support` | Cerca supporto |
| `gives_support` | Dà supporto |
| `unspecified` | Non specificato |

**Da chiarire in videocall:** la conversione dei valori attuali. `activist` → `gives_support` è
ragionevole, ma `citizen` → `seeks_support` **non** è ovvio: "cittadino" non implica che cerchi
supporto. Ci sono solo 3 contatti, quindi si può anche decidere caso per caso.

### Campo B — ruolo operativo, multiplo

Due tabelle, stesso schema dei gruppi:

```sql
CREATE TABLE res_partner_role (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  code       text NOT NULL UNIQUE,
  label_it   text NOT NULL,
  sort_order int  NOT NULL DEFAULT 0,
  status     text NOT NULL DEFAULT 'active' CHECK (status IN ('active','inactive'))
);

CREATE TABLE res_partner_role_rel (
  partner_id uuid NOT NULL REFERENCES res_partner(id) ON DELETE CASCADE,
  role_id    uuid NOT NULL REFERENCES res_partner_role(id) ON DELETE CASCADE,
  PRIMARY KEY (partner_id, role_id)
);
CREATE INDEX idx_pr_rel_role ON res_partner_role_rel(role_id);
```

Tabella invece di un enum perché il cliente aggiungerà voci: così le gestisce dalla UI senza
migrazione.

Seed:

| code | label_it |
|---|---|
| `famiglia_ospitante` | Famiglia ospitante |
| `specialista_abitare` | Specialista diritti sull'abitare |
| `specialista_migrazione` | Specialista diritti sulla migrazione |
| `membro_semplice` | Membro semplice della comunità |
| `bussola` | Bussola |

**Nota:** "persona che cerca supporto" era nell'elenco del punto 7, ma **non va messa fra i
ruoli**: ora è il campo A. Tenerla in entrambi creerebbe due fonti in conflitto per lo stesso
dato. Da confermare al cliente.

"Specialista di diritti sull'abitare **e/o** sulla migrazione" è spezzato in due voci proprio
perché la selezione è multipla e l'"e/o" diventa rappresentabile.

### ⚠️ RLS delle tabelle nuove

Devono seguire il modello di `privacy_consent` **dopo** la correzione del 2026-07-25:

```sql
USING      (can_see_partner(auth.uid(), partner_id))
WITH CHECK (can_see_partner(auth.uid(), partner_id))
```

**Non** ripetere l'errore di `WITH CHECK (true)` / `WITH CHECK (current_role_name() IS NOT NULL)`:
è esattamente il buco chiuso in `20260725120000`. Dopo averle create, rilanciare
`.claude/rls-tests.sql`.

## Punto 10 — Tessera preesistente nel form

**Decisione presa** (upsert): il form ha un campo facoltativo "numero tessera".

```
numero tessera fornito?
├── no  → flusso attuale
└── sì  → cerca in membership_subscription
         ├── trovata     → associa e aggiorna i dati del contatto
         └── non trovata → crea il contatto SENZA tessera, e avvisa nel form:
                           "tessera non trovata: ti registriamo comunque, il numero
                            verrà corretto o ti verrà assegnata una nuova tessera"
```

La RPC restituisce un flag in più, es. `membership_found: true|false`, così il form mostra
l'avviso.

### ⚠️ Caveat da portare in videocall

`membership_number` è UNIQUE, quindi ogni codice identifica **una** tessera, che è già legata a
un `partner_id`. Se qualcuno inserisce il numero di tessera **di un altro socio** — per errore o
deliberatamente — l'associazione trasferirebbe quella tessera a sé.

Regola che propongo: se la tessera esiste **ed è già legata a un partner con email diversa**,
non riassegnarla. Creare il contatto, mettere il numero in un campo "da verificare" e mandarlo in
`Validation`. Coerente con lo spirito della decisione ("verrà poi corretto") e senza il rischio
di scippo.
